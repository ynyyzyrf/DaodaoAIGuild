# 龍蝦騎士社區｜需求訂單履約 MVP 需求文檔

---

# 1. 文檔目的

本文檔定義龍蝦騎士社區下一階段的「需求訂單履約 MVP」。

本階段基於既有代碼中的人與組織能力，先跑通紅框內的最小商業閉環：

```text
企業提交需求
↓
FDE 社區管理員審核
↓
進入機會池
↓
咨詢公司接單 / 申請承接
↓
管理員確認承接方
↓
咨詢公司報價與排期
↓
企業確認合作
↓
模擬支付
↓
交付與驗收
↓
評價與 Profile 沉澱
```

第一版不追求完整交易平台，而是驗證：

> 企業需求是否能通過 DaoStore / 龍蝦騎士社區，被已入駐咨詢公司承接，並形成可追蹤、可驗收、可沉澱的履約記錄。

# 2. 既有代碼基礎

本需求應復用現有 Next.js + FastAPI + MySQL 架構，不重做身份和公司模型。

## 2.1 已有後端基礎

現有後端已具備以下能力：

* `User`
  * 自然人帳號。
  * 已有 `is_admin`、`is_verified_fde`、`level`、`reputation`、`exp` 等字段。

* `Company`
  * 咨詢公司是一級業務對象，不是 User Profile 上的公司名稱字符串。
  * 已有公司入駐資料、審核狀態、審核備註、提交時間、審核時間。

* `CompanyMember`
  * 已建模 User 與 Company 的組織關係。
  * `company_role` 表示公司內 Owner / Admin / none。
  * `fde_status` 表示 FDE 與咨詢公司的正式歸屬狀態。
  * 公司角色與 FDE 正式歸屬是兩個維度，但必須對齊到同一家公司。

* `CompanyJoinRequest`
  * 已支持 FDE 主動申請加入已審核通過的咨詢公司。
  * 同一 FDE 同時只能有一個待處理申請，最多一個 active 正式所屬咨詢公司。

* 管理後台
  * 已有公司審核接口和審核日志模式。
  * 後續訂單審核也應延續後台治理思路。

## 2.2 已有前端基礎

現有前端已具備以下頁面/能力：

* 公司公開列表與公司詳情。
* 咨詢公司入駐頁。
* 咨詢公司中心。
* 公司 Owner / Admin 管理加入申請與龍蝦騎士歸屬。
* 管理後台公司審核入口。
* 個人 Profile、聲望、成就與遊戲化基礎。

## 2.3 本階段新增能力與既有模型關係

本階段新增的核心對象是：

* 企業需求 / 訂單
* 機會池
* 承接申請 / 接單記錄
* 報價與排期
* 模擬支付記錄
* 交付驗收記錄
* 評價與履約 Profile 記錄

其中：

* 咨詢公司必須復用現有 `Company`。
* 咨詢公司操作人必須復用現有 `CompanyMember.company_role in ("owner", "admin")`。
* 龍蝦騎士 / FDE 必須復用現有 `User.is_verified_fde` 與 `CompanyMember.fde_status = "active"`。
* 第一版不新增分賬模型。

# 3. 本階段定位

## 3.1 產品定位

本階段不是內容社區功能，也不是完整 DaoStore 支付結算系統。

本階段是：

> 龍蝦騎士社區中的 FDE 訂單履約工作台 MVP。

它承接企業正式需求，讓需求被審核、進入機會池、由咨詢公司承接、完成報價、模擬支付、交付驗收和評價沉澱。

## 3.2 業務原則

* 機會池是正式企業需求入口，不從問題廣場或龍蝦房間轉化。
* 咨詢公司是接單與履約責任主體。
* 龍蝦騎士 / FDE 是交付執行主體。
* FDE 社區管理員負責審核、秩序、承接方確認和信用治理。
* A coin 第一版不深度接入，只做模擬支付狀態。
* 分賬第一版不做。
* 所有履約結果應能沉澱到企業、咨詢公司和 FDE 的 Profile / 信用記錄中。

# 4. 角色與權限

本階段確認 4 類業務角色。

## 4.1 企業

企業代表需求方。

第一版可以先復用普通 User 作為企業操作人，後續再補企業組織模型。

可以：

* 創建需求訂單。
* 查看自己提交的訂單。
* 補充需求資料。
* 查看審核結果。
* 查看咨詢公司報價與排期。
* 確認合作。
* 查看模擬支付狀態。
* 確認驗收。
* 提交評價。

不可以：

* 查看其他企業的訂單。
* 直接選擇未被管理員確認的承接方。
* 修改咨詢公司報價。
* 操作平台審核、接單確認、結算。

## 4.2 FDE 社區管理員

復用現有 `User.is_admin = true`。

可以：

* 查看全部需求訂單。
* 審核企業需求。
* 將通過審核的需求放入機會池。
* 駁回不合格需求並要求補充。
* 查看咨詢公司的承接意向。
* 確認最終承接咨詢公司。
* 模擬標記支付成功。
* 查看交付和驗收狀態。
* 觸發訂單結算狀態。
* 查看評價與履約沉澱。

不可以：

* 代替咨詢公司填寫商業報價。
* 代替企業確認合作或驗收。
* 強制改變既有 Company/FDE 歸屬關係。

## 4.3 咨詢公司

咨詢公司是一級業務對象，復用現有 `Company`。

實際操作人必須是該公司的 Owner / Admin。

可以：

* 查看機會池。
* 對需求表達承接意向。
* 在被確認為承接方後，分配本公司 active 龍蝦騎士 / FDE 跟進。
* 填寫報價與排期。
* 提交交付物說明。
* 提交驗收申請。
* 查看支付與訂單狀態。
* 查看企業評價。

不可以：

* 承接未進入機會池的需求。
* 承接未被管理員確認給自己的訂單。
* 分配不屬於本公司的 active FDE。
* 修改企業確認後的報價關鍵字段，除非走重新報價流程。

## 4.4 龍蝦騎士 / FDE

復用現有 `User.is_verified_fde = true`。

第一版只允許被所屬咨詢公司分配到訂單跟進。

可以：

* 查看分配給自己的需求跟進任務。
* 查看需求背景、交付範圍、排期和企業配合事項。
* 更新跟進備註。
* 標記任務進度。
* 在訂單完成後獲得 Profile 履約記錄。

不可以：

* 直接搶單。
* 直接向企業報價。
* 直接代表咨詢公司確認合作。
* 自行解除公司歸屬來規避訂單責任。

# 5. 訂單狀態機

## 5.1 主狀態

第一版訂單主狀態如下：

```text
draft
↓
pending_review
↓
opportunity_pool
↓
claimed
↓
requirement_following
↓
quoted
↓
confirmed
↓
pending_payment
↓
paid
↓
delivering
↓
pending_acceptance
↓
accepted
↓
settled
↓
rated
```

## 5.2 中文顯示

| 狀態 | 中文名 | 說明 |
| --- | --- | --- |
| `draft` | 草稿 | 企業正在編輯，尚未提交 |
| `pending_review` | 待審核 | 企業已提交，等待管理員審核 |
| `opportunity_pool` | 機會池 | 管理員審核通過，咨詢公司可查看/申請承接 |
| `claimed` | 已確認承接方 | 管理員已確認承接咨詢公司 |
| `requirement_following` | 需求跟進中 | 咨詢公司 / FDE 正在澄清需求 |
| `quoted` | 已報價 | 咨詢公司已提交報價與排期 |
| `confirmed` | 已確認合作 | 企業接受報價 |
| `pending_payment` | 待支付 | 等待支付完成 |
| `paid` | 已支付 | 模擬支付成功 |
| `delivering` | 交付中 | 咨詢公司組織交付 |
| `pending_acceptance` | 待驗收 | 咨詢公司提交交付，等待企業驗收 |
| `accepted` | 已驗收 | 企業確認交付通過 |
| `settled` | 已結算 | 第一版僅標記訂單完成結算，不做分賬 |
| `rated` | 已評價 | 企業/咨詢公司/FDE 評價沉澱完成 |

## 5.3 必要異常狀態

第一版只保留 3 個必要異常狀態：

| 狀態 | 中文名 | 觸發人 | 說明 |
| --- | --- | --- | --- |
| `review_rejected` | 審核駁回 | 管理員 | 需求不合格，企業可修改後重提 |
| `quote_revision_required` | 報價退回修改 | 企業 | 企業要求調整報價/排期 |
| `acceptance_rejected` | 驗收不通過 | 企業 | 交付物未通過，回到交付中 |

## 5.4 狀態流轉表

| 當前狀態 | Owner | 可執行動作 | 下一狀態 |
| --- | --- | --- | --- |
| `draft` | 企業 | 提交需求 | `pending_review` |
| `pending_review` | 管理員 | 審核通過 | `opportunity_pool` |
| `pending_review` | 管理員 | 駁回 | `review_rejected` |
| `review_rejected` | 企業 | 修改後重提 | `pending_review` |
| `opportunity_pool` | 咨詢公司 | 申請承接 | 狀態不變，生成承接意向 |
| `opportunity_pool` | 管理員 | 確認承接方 | `claimed` |
| `claimed` | 咨詢公司 | 分配跟進 FDE | `requirement_following` |
| `requirement_following` | 咨詢公司 | 提交報價與排期 | `quoted` |
| `quoted` | 企業 | 接受報價 | `confirmed` |
| `quoted` | 企業 | 要求修改 | `quote_revision_required` |
| `quote_revision_required` | 咨詢公司 | 重新報價 | `quoted` |
| `confirmed` | 系統 | 生成待支付記錄 | `pending_payment` |
| `pending_payment` | 管理員 / 模擬支付服務 | 標記已支付 | `paid` |
| `paid` | 咨詢公司 | 開始交付 | `delivering` |
| `delivering` | 咨詢公司 | 提交驗收 | `pending_acceptance` |
| `pending_acceptance` | 企業 | 驗收通過 | `accepted` |
| `pending_acceptance` | 企業 | 驗收不通過 | `acceptance_rejected` |
| `acceptance_rejected` | 咨詢公司 | 重新提交驗收 | `pending_acceptance` |
| `accepted` | 管理員 | 標記結算 | `settled` |
| `settled` | 企業/咨詢公司/FDE | 提交評價 | `rated` |

# 6. 機會池規則

## 6.1 進入機會池

需求必須滿足：

* 企業已提交完整需求。
* 管理員審核通過。
* 需求狀態為 `opportunity_pool`。

只有 `opportunity_pool` 狀態的需求出現在機會池。

## 6.2 承接方式

第一版採用：

> 咨詢公司表達承接意向，管理員確認最終承接方。

規則：

* 一個需求可以有多個咨詢公司表達承接意向。
* 一個需求最終只能有一個承接咨詢公司。
* 只有 approved Company 可以承接。
* 只有該 Company 的 Owner / Admin 可以操作承接。
* 管理員確認後，需求離開公開機會池，進入 `claimed`。

## 6.3 暫不支持

* 企業直接挑選咨詢公司。
* 完全自由搶單。
* 多家咨詢公司共同承接同一訂單。
* 龍蝦騎士個人直接承接。

# 7. 報價與排期

咨詢公司在需求跟進後提交報價。

報價至少包含：

* 報價金額。
* 幣種，第一版可固定為 `CNY` 或 `A_COIN_SIMULATED`。
* 預計開始時間。
* 預計交付時間。
* 交付範圍。
* 交付物清單。
* 不包含內容。
* 風險說明。
* 需要企業配合事項。
* 咨詢公司負責人。
* 參與龍蝦騎士 / FDE。

報價一旦被企業確認，關鍵字段不可直接修改。

如需修改，應由企業退回到 `quote_revision_required`，咨詢公司重新提交報價。

# 8. 支付 MVP

## 8.1 支付策略

第一版只做模擬支付。

企業確認報價後：

```text
confirmed
↓
pending_payment
↓
paid
```

`paid` 由管理員或模擬支付服務標記。

## 8.2 支付記錄字段

至少記錄：

* 訂單 ID。
* 應支付金額。
* 支付狀態：`pending` / `paid` / `failed` / `cancelled`。
* 支付方式：第一版固定為 `simulated`。
* 支付時間。
* 操作人。
* 支付備註 / 憑證備註。

## 8.3 後續 A coin 接入預留

後續接 A coin 時，應保留：

* 外部支付單號。
* 支付回調 ID。
* 支付回調原始摘要。
* 支付渠道狀態。

但第一版不實現。

# 9. 分賬與結算

## 9.1 第一版不做分賬

本階段不做：

* 分賬比例配置。
* 咨詢公司 / FDE / 平台自動分潤。
* 提現。
* 錢包。
* A coin 真實劃撥。

## 9.2 第一版結算含義

第一版的 `settled` 只表示：

> 該訂單已完成交付驗收，平台已將其標記為結算完成。

結算字段至少包含：

* 訂單 ID。
* 結算狀態：`pending` / `settled`。
* 結算時間。
* 操作管理員。
* 結算備註。

# 10. 評價與 Profile 沉澱

## 10.1 評價對象

第一版評價至少支持：

* 企業評價咨詢公司。
* 企業評價交付結果。
* 咨詢公司評價參與 FDE。
* 管理員補充治理評價。

## 10.2 評價字段

至少包含：

* 訂單 ID。
* 評價人 ID。
* 評價人角色。
* 被評價對象類型：`company` / `fde` / `delivery`。
* 被評價對象 ID。
* 評分，建議 1-5。
* 評價內容。
* 是否可公開展示。
* 創建時間。

## 10.3 FDE Profile 沉澱

訂單完成後，應為參與 FDE 形成履約記錄。

履約記錄至少包含：

* 訂單 ID。
* FDE User ID。
* 所屬咨詢公司 ID。
* 項目名稱 / 需求標題。
* 所屬產品。
* 項目類型。
* 擔任角色。
* 交付週期。
* 技能標籤。
* 企業評分。
* 咨詢公司評分。
* 是否可公開為案例。
* 完成時間。

第一版可以先獨立建履約記錄表，不必立即改造現有遊戲化算法。

後續可再將完成項目數、評價、案例公開狀態接入聲望、成就、排行榜。

# 14. 權限校驗規則

## 14.1 企業訂單權限

* 訂單創建人可以查看自己的訂單。
* 訂單創建人可以在 `draft`、`review_rejected` 修改需求。
* 訂單創建人可以在 `quoted` 確認報價或要求修改。
* 訂單創建人可以在 `pending_acceptance` 驗收或駁回。

## 14.2 管理員權限

* 只有 `is_admin = true` 可審核訂單。
* 只有管理員可確認承接方。
* 只有管理員可模擬標記支付。
* 只有管理員可標記結算。

## 14.3 咨詢公司權限

* 只有 approved Company 可承接訂單。
* 只有公司 Owner / Admin 可代表公司承接。
* 只有被選中的公司可報價、分配 FDE、提交交付。
* 被分配 FDE 必須是該公司 active Lobster Knight。

## 14.4 FDE 權限

* FDE 只能查看分配給自己的任務。
* FDE 任務更新不得直接推進訂單商業狀態。
* 訂單商業狀態由企業、咨詢公司 Owner/Admin、管理員推進。

# 15. 驗收標準

## 15.1 需求提交與審核

* [ ] 企業可以創建需求草稿。
* [ ] 企業可以提交需求審核。
* [ ] 管理員可以查看待審核需求。
* [ ] 管理員可以審核通過，使需求進入機會池。
* [ ] 管理員可以駁回需求，企業可修改後重提。

## 15.2 機會池與承接

* [ ] 只有審核通過的需求出現在機會池。
* [ ] 已審核通過的咨詢公司 Owner/Admin 可以表達承接意向。
* [ ] 非公司 Owner/Admin 不可代表公司承接。
* [ ] 管理員可以查看多個承接意向。
* [ ] 管理員可以確認唯一承接咨詢公司。

## 15.3 需求跟進與報價

* [ ] 承接公司可以分配本公司 active FDE。
* [ ] 不屬於該公司的 FDE 不可被分配。
* [ ] 咨詢公司可以提交報價與排期。
* [ ] 企業可以確認報價。
* [ ] 企業可以要求修改報價。

## 15.4 模擬支付

* [ ] 企業確認報價後生成待支付記錄。
* [ ] 管理員可以模擬標記已支付。
* [ ] 已支付訂單進入可交付狀態。
* [ ] 第一版不調用真實 A coin。

## 15.5 交付、驗收與結算

* [ ] 咨詢公司可以提交交付物說明。
* [ ] 企業可以驗收通過。
* [ ] 企業可以駁回驗收並要求補交。
* [ ] 管理員可以在驗收通過後標記結算。
* [ ] 第一版結算不產生分賬。

## 15.6 評價與 Profile

* [ ] 訂單結算後可以提交評價。
* [ ] 評價包含分數、內容、對象和公開狀態。
* [ ] 參與 FDE 可以獲得項目履約記錄。
* [ ] 履約記錄可用於後續 Profile、案例、信用、排行榜擴展。
