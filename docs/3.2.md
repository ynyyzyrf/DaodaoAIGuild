# DaoDao FDE 社區 3.2 需求文檔
## 管理後臺（Admin Console）

**版本：** V3.2
**產品：** DaoDao FDE Community / 龍蝦騎士社區
**版本重點：** 為運營 / 社區管理員提供一套**輕量、簡單、夠用**的內部管理控制台，把「人、內容、任務、配置」四條線管起來。

---

# 1. 版本背景與目標

## 1.1 為什麼做管理後臺

V1.0 / V2.0 / V3.0 已上線核心社區能力，**目前所有運營操作都依賴 seed 腳本直連資料庫**：

- 創建管理員 → 改 `seed_admin.py` 跑腳本
- 審核教程 → 改 `tutorials.status` 欄位
- 處理舉報 → 沒有對應流程
- 處理違規用戶 → 改 `users.is_active`
- 調整任務 → 改 `missions` 欄位

這種方式：

- ❌ 效率低、容易出錯
- ❌ 沒有操作留痕，無法追溯誰改過什麼
- ❌ 隨著用戶量增加，運營成本指數級上升

因此 V3.2 的目標是：

> **把「後台管理」從「改資料庫」變成「點滑鼠」。**

## 1.2 核心目標

只做 3 件事：

1. **審核內容**：處理被舉報 / 敏感詞命中的問題與回答；預審所有教程
2. **管理用戶**：啟用 / 停用、改等級、調聲望、標記官方 FDE
3. **管理任務**：強制轉派、改狀態、釋放超期

其他能力（報表、標籤、媒體、生態配置）**全部放到 P1 / P2**。

## 1.3 設計原則

- **簡單**：不做企業級 RBAC，1 種管理員角色
- **安全**：所有寫操作必須留痕
- **可逆**：軟刪除為主，重要操作填原因
- **克制**：不在後台堆疊遊戲化元素，後台是工具不是產品

# 2. 角色與權限

## 2.1 只保留 1 種角色

| 角色 | 標識 | 權限 |
|---|---|---|
| 管理員 | `users.is_admin = true` | 後台全部模組 |

不擴充 `role` 字段，不引入權限點 / 權限矩陣。

理由：

- MVP 階段管理員數量 ≤ 5 人，無需細粒度權限
- 簡化資料庫 schema，簡化後端依賴注入
- 後續若需要拆分，可平滑引入 `role` 字段

## 2.2 管理員創建方式

**全部走 `seed_admin.py` 腳本**，後台不開放「創建管理員」入口。

理由：

- 避免越權（管理員不能自己提權）
- 冷啟動期管理員數量極少，腳本方式足夠
- 符合既有約定（V1.0 已使用此方式）

後續若需要批量管理，再單獨加一個「後台創建管理員」按鈕（不在 V3.2 範圍）。

## 2.3 首個管理員

沿用 V1.0 既定方案：

```bash
python scripts/seed_admin.py
```

腳本中預置的 `admin` 帳號即為首位管理員。

# 3. 部署形態

## 3.1 同站子路由

管理後台是**主站點的一個子路由組**：

```
web/app/
  (public)/...           # 用戶前台
  (auth)/...             # 用戶登入
  admin/                 # 管理後台（新增）
    layout.tsx           # 後台專用 Layout（側邊欄 + 頂部欄）
    page.tsx             # 儀表板（M2 入口）
    users/page.tsx       # 用戶管理
    moderation/page.tsx  # 內容審核
    missions/page.tsx    # 任務管理
    audit/page.tsx       # 稽核日誌
    settings/...         # P2 配置
```

理由：

- 共用 Next.js 構建產物
- 共用部署流水線
- 共用登入態（JWT）
- 開發者心智成本低

## 3.2 API 隔離

後台 API 走獨立前綴：

```
/api/v1/*           用戶前台 API（已有）
/api/v1/admin/*     管理後台 API（新增）
```

所有 `/api/v1/admin/*` 接口統一走 `Depends(require_admin)` 依賴，未通過拋 401。

## 3.3 路由保護

`web/app/admin/**` 下的所有 Server Component 統一校驗：

```text
if session.user.is_admin !== true:
  redirect("/403")
```

建議封裝成 `web/app/admin/layout.tsx` 頂層攔截，避免每個頁面重複判斷。

## 3.4 入口

後台**不在用戶前台導航欄露出**。管理員透過以下方式進入：

- 直接訪問 `/admin`
- 或登入後訪問 `/admin` 自動跳轉

# 4. 內容審核策略

這是 V3.2 最關鍵的決策之一。

## 4.1 兩種審核流

| 內容類型 | 審核策略 | 進入審核佇列的觸發條件 |
|---|---|---|
| 問題（questions） | **先發後審** | 被舉報 / 敏感詞命中 |
| 回答（answers） | **先發後審** | 被舉報 / 敏感詞命中 |
| 教程（tutorials） | **預審**（必走審核） | 所有新教程預設 `status=pending` |
| Solution | **V3.2 不做** | 暫不涉及 |

### 4.1.1 為什麼教程必須預審

教程是「知識沉澱」，會長期留在社區並被搜索 / 引用。一旦出現錯誤、抄襲、敏感內容，下架成本高。

問題 / 回答是「即時互動」，用戶能在評價中自然淘汰低質內容，且閱讀量隨時間衰減，下架成本低。

## 4.2 統一審核佇列

雖然觸發條件不同，但**所有需要審核的內容走同一個審核 UI**：

- 篩選器：類型（問題/回答/教程）+ 狀態 + 時間
- 單條詳情面板：內容預覽、作者信息、舉報原因、敏感詞命中位置
- 操作按鈕：
  - 問題 / 回答：通過 / 隱藏 / 刪除
  - 教程：通過 / 打回（附理由） / 刪除

## 4.3 敏感詞系統

### 4.3.1 數據模型

新建 `sensitive_words` 表：

| 字段 | 類型 | 說明 |
|---|---|---|
| id | BIGINT PK | |
| word | VARCHAR(64) UNIQUE | 敏感詞 |
| category | VARCHAR(32) | 分類（如：政治 / 色情 / 暴力 / 廣告 / 自定義） |
| action | ENUM | `warn`（標紅警告）/ `auto_hide`（自動隱藏） |
| is_active | BOOL | 啟用開關 |
| created_by | BIGINT FK→users | 創建者 |
| created_at / updated_at | DATETIME | |

### 4.3.2 命中策略

- 內容創建 / 編輯時，後端做正則匹配
- 命中 `warn` 詞：內容正常發布，但前端標紅 + 自動進入審核佇列
- 命中 `auto_hide` 詞：內容不展示（前端看不到），自動進入審核佇列

### 4.3.3 後台管理

- 敏感詞列表 CRUD
- 支持批量導入（TXT 格式，每行一個詞）
- 操作記錄寫入稽核日誌

# 5. 核心模組（P0）

> V3.2 開發只做 P0 模組。P1 / P2 見 §6。

## 5.1 M1 — 登入 / 登出

### 功能

- 共用 `/api/v1/auth/login` 登入
- 登入成功後校驗 `is_admin`，否則提示「無後台權限」
- 後台 session 有效期 **1 小時**（短於普通用戶的 2 小時）

### 安全

- 登入失敗 5 次鎖定 15 分鐘（按 username 維度）
- 鎖定狀態記在記憶體或 Redis，**MVP 階段先用記憶體**
- 所有登入嘗試寫入稽核日誌（成功 / 失敗 / 鎖定）

### 介面

- 登入頁 `web/app/admin/login/page.tsx`
- 沿用前台登入 UI（從 `web/app/(auth)/login/page.tsx` 復用組件）

## 5.2 M2 — 儀表板

後台首頁。**一眼看出社區健康度與待辦。**

### 5.2.1 核心指標卡（4 個）

| 指標 | 顏色 | 含義 |
|---|---|---|
| 待審核教程數 | 紅色高亮 | 當前 `status=pending` 的教程 |
| 今日新增 | 中性 | 問題 + 回答 + 教程合計 |
| 進行中任務數 | 中性 | `missions.status=in_progress` |
| 近 7 日活躍騎士 | 中性 | 近 7 日有發問/回答/教程的用戶 |

### 5.2.2 30 日趨勢圖

折線圖，三條線：

- 問題
- 回答
- 教程

來源：聚合查詢 `created_at >= now() - 30d`，按天分組。

### 5.2.3 待審核佇列直達入口

- 待審教程（按時間倒序，Top 10）
- 被舉報的問題/回答（Top 10）
- 敏感詞命中（Top 10）

每條點擊直達審核詳情頁。

### 5.2.4 異常預警

- **24h 新發布但 0 回答的問題**：可能無人關注或內容太難
- **超期未交付任務**：`status=in_progress` 且 `updated_at < now() - 7d`
- **短時間大量相似內容**（V1 可關閉）：同一作者 1h 內發布 ≥ 3 條相似內容

### 5.2.5 介面

`web/app/admin/page.tsx`（儀表板）

## 5.3 M3 — 用戶管理

### 5.3.1 列表

**欄位**：用戶名 / display_name / 等級 / 聲望 / 狀態 / 註冊時間 / 最後活躍

**篩選**：

- 等級（1–5 多選）
- 活躍度（近 7 日 / 30 日 / 90 日 / 從不）
- 狀態（啟用 / 停用）
- 是否管理員

**搜索**：用戶名 / display_name 模糊匹配

**分頁**：每頁 20 條

### 5.3.2 詳情

**基本資料**：

- 用戶名、display_name、頭像、簡介
- 等級、聲望
- 註冊時間、最後活躍時間
- 是否管理員、是否官方認證 FDE

**統計**：

- 發問數 / 回答數 / 教程數 / Solution 數 / 接單任務數
- 採納數 / 收藏數 / 點讚數

**違規記錄**（V1 可簡化為：曾被刪除的內容計數）

### 5.3.3 操作

| 操作 | 說明 | 必填原因 |
|---|---|---|
| 啟用 / 停用 | 切換 `is_active` | ✅ |
| 重置密碼 | 生成隨機 12 位密碼，**後台一次性顯示** | — |
| 修改等級 | 手動覆蓋 1–5 | ✅ |
| 調整聲望 | ±N（N ≤ 1000） | ✅ |
| 標記 / 取消官方 FDE | 切換 `is_verified_fde` | ✅ |
| 軟刪除 | 匿名化 display_name、avatar_url、bio，**保留記錄** | ✅ |

> 所有操作寫入稽核日誌。

### 5.3.4 介面

- 列表 `web/app/admin/users/page.tsx`
- 詳情 `web/app/admin/users/[id]/page.tsx`
- 操作確認 Drawer：右側滑出，包含表單 + 原因輸入 + 預覽影響

## 5.6 M6 — 稽核日誌

### 5.6.1 數據模型

新建 `admin_audit_logs` 表：

| 字段 | 類型 | 說明 |
|---|---|---|
| id | BIGINT PK | |
| admin_id | BIGINT FK→users | 操作者 |
| action | VARCHAR(64) | 操作類型（如 `user.disable` / `tutorial.approve`） |
| target_type | VARCHAR(32) | 對象類型（`user` / `question` / `answer` / `tutorial` / `mission` / `sensitive_word`） |
| target_id | BIGINT | 對象 ID |
| before_value | JSON | 操作前的值 |
| after_value | JSON | 操作後的值 |
| reason | TEXT | 必填的操作原因 |
| ip | VARCHAR(64) | 操作者 IP |
| created_at | DATETIME | |

**索引**：`admin_id`、`target_type + target_id`、`created_at`。

### 5.6.2 自動記錄

通過 FastAPI 中間件自動捕獲所有 `/api/v1/admin/*` 下的寫操作，業務代碼無需手動調用。

**記錄規則**：

- 讀操作（GET）**不記**
- 寫操作（POST / PUT / PATCH / DELETE）**全部記**
- 登入 / 登出 單獨記 `auth.login` / `auth.logout` / `auth.locked`

### 5.6.3 介面

- 列表 `web/app/admin/audit/page.tsx`
- 篩選：操作者 / 對象類型 / 時間區間
- 每條可展開看 before / after diff

### 5.6.4 保留期

**永久保留**（稽核日誌不應被清理）。

若未來資料量過大，可改為冷存儲歸檔，但不做自動刪除。

# 7. 視覺與 UX 原則

## 7.1 風格沿用

完全沿用 [UI-STYLE.md](./UI-STYLE.md)：

- 白色 + 極淺灰背景
- DaoClaw 磚紅 `#C5573C` 為主操作色
- 細邊框 + 輕陰影 + 中等圓角
- `lucide-react` 線性圖標

**龍蝦元素只在後台空狀態點綴**（如「🦞 目前沒有待審內容」），不堆疊。

## 7.2 後台特有佈局

```
┌────────────────────────────────────────────────────────────┐
│  🦞 DaoDao Admin                          [🔔] [👤 管理員 ▾] │  ← 頂部欄（56px）
├──────────┬─────────────────────────────────────────────────┤
│          │                                                 │
│ 📊 儀表板 │                                                 │
│ 👥 用戶   │              主 內 容 區                         │
│ 🛡️ 審核   │                                                 │
│ 📋 任務   │                                                 │
│ 📜 日誌   │                                                 │
│          │                                                 │
│ ⚙️ 設置   │                                                 │
│          │                                                 │
└──────────┴─────────────────────────────────────────────────┘
   240px
```

- 側邊欄寬度 240px，固定
- 頂部欄高 56px，固定
- 主內容區最大寬度 1440px，自動居中
- 列表用緊湊表格（行高 40–48px），比前台更密

## 7.3 交互細節

- **破壞性操作必須二次確認 + 填原因**：刪除、停用、調聲望、改等級
- **批量操作必須顯示影響摘要**：「將通過 12 條內容，操作不可撤銷」
- **列表支持列選擇記憶**（用戶可隱藏不關心的列）
- **大表必備篩選器抽屜**（右側滑出），不要每列一個 dropdown
- **行內操作走 Drawer / Modal**，不跳轉頁面
- **Loading / Empty / Error 三態完整**：
  - Loading：骨架屏
  - Empty：🦞 空狀態插圖 + 提示文案
  - Error：錯誤信息 + 重試按鈕

## 7.4 反例（不要做）

- ❌ 後台用大字號 / 大色塊 / 卡通化
- ❌ 龍蝦元素堆滿每個角落
- ❌ 表格列過寬，導致一行只顯示 3 條
- ❌ 任何操作無確認直接執行
- ❌ 重要篩選器藏在二級菜單

# 8. 數據模型變更

## 8.1 新增表

### `admin_audit_logs`（見 §5.6.1）

CREATE TABLE admin_audit_logs (

# 10. 安全

## 10.1 二次確認 + 必填原因

所有下列操作，UI 必須彈出確認對話框，**且必須填寫原因**：

- 刪除任何內容
- 停用用戶
- 修改用戶等級
- 調整用戶聲望
- 強制轉派任務
- 修改任務狀態

原因不填 → 按鈕 disabled。

## 10.2 稽核日誌不可刪

`admin_audit_logs` 表不對外暴露刪除 / 更新 API。僅可追加。

## 10.3 登入鎖定

- 連續 5 次密碼錯誤，鎖 15 分鐘（按 username）
- 鎖定期間即使密碼正確也拒絕登入
- 鎖定事件寫入稽核日誌

## 10.4 Session 短有效期

- 後台 JWT 有效期 1 小時
- 閒置 30 分鐘後自動登出（前端可選實作）

## 10.5 IP 記錄

每次操作記錄 IP，輔助異常檢測。

# 13. 風險與開放問題

| # | 事項 | 影響 | 決策 |
|---|---|---|---|
| 1 | 登入鎖定用記憶體實現，多實例部署失效 | 多實例時鎖定失效 | MVP 接受，後續接 Redis |
| 2 | 稽核日誌大量增長 | 查詢慢 | MVP 接受，後續歸檔冷存儲 |
| 3 | 敏感詞匹配性能 | 大內容可能慢 | MVP 用正則簡單匹配，後續考慮 AC 自動機 |
| 4 | 教程預審可能積壓 | 教程發布延遲 | MVP 接受，後續加「超 X 天自動通過」規則 |
| 5 | 1 種管理員，無法隔離「能刪教程但不能刪用戶」 | 信任風險 | MVP 接受，依賴管理員自律 + 稽核追溯 |
| 6 | 後台嵌入主站，後台 CSS 污染前台 | 視覺 bug | 通過路由組隔離（admin 路由組專用 layout） |
| 7 | 缺少批量操作的任務化 | 大批量操作前端卡頓 | MVP 接受 100 條以內，後續加任務化 |
| 8 | 用戶舉報的去重 | 同一用戶多次舉報同內容 | DB UNIQUE 約束保證 |
| 9 | 「重置密碼後台一次性顯示」安全風險 | 密碼可能被截屏 | 後續改為「發送郵件 / 飛書通知」（不在 V3.2 範圍） |
