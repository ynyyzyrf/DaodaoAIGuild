# DaoStore 系統介紹視頻錄製稿

建議成片時長：5-7 分鐘
錄製方式：瀏覽器錄屏 + 口播講解
講解主線：從一個企業需求進入 DaoStore 開始，展示需求方、管理員、咨詢公司、龍蝦騎士如何共同完成交付閉環。

## 開場總覽

建議畫面：首頁 `/`

旁白：

大家好，這段視頻帶大家從用戶角度看一下 DaoStore 這套系統。

DaoStore 不是一個單純展示方案的商城，它更像是企業 AI Solution 的交付協作平台。企業可以把需求說清楚，平台管理員負責審核和治理，咨詢公司作為承接方負責組織交付，龍蝦騎士作為 FDE 交付者負責把需求真正推進到方案、集成、部署和驗收。

今天我會按四個身份走一遍：需求方、管理員、咨詢公司、龍蝦騎士。你會看到這套系統的重點不是展示概念，而是把需求從提交、審核、承接、分派、跟進到交付狀態串起來。

## 一、需求方視角

建議畫面：`/chat`，再切到 `/orders`

旁白：

我們先站在需求方角度。

需求方最常見的第一步，不是先研究後台菜單，而是直接把業務問題說出來。比如我想做一個經銷商開發 Agent，或者我有一個企業內部流程想用 AI 改造。進入需求對話頁後，可以直接用自然語言描述需求。

系統會先幫我把需求整理成可確認的信息，而不是馬上丟進後台。這裡有一個很重要的設計：需求方需要確認需求名稱、要解決的問題、背景、公司或產品信息。只有確認後，需求才正式進入流程。

提交後，需求方可以在「企業需求工作台」看到自己的需求狀態。這裡不是一個黑盒，需求會經過待審核、機會池、已確認承接方、需求跟進、報價、交付驗收等階段。

對需求方來說，核心價值是三件事：第一，需求不用自己翻譯成技術任務；第二，狀態是可追蹤的；第三，承接方和交付進度都可以在同一條鏈路上看到。

錄屏操作點：

- 打開 `/chat`，展示「需求對話」和 DaoStore 小助手。
- 說一句示例需求，例如「我要提交一個經銷商開發 Agent 的需求」。
- 展示需求待確認區域。
- 切到 `/orders`，展示企業需求工作台和狀態流轉。

## 二、管理員視角

建議畫面：`/admin/orders`、`/admin/companies`、`/admin/solutions`

旁白：

接著看管理員。

管理員在這套系統裡不是只做賬號管理，而是負責平台的交易和供給治理。第一個入口是需求訂單。當需求方提交需求後，管理員需要判斷這個需求是否完整，是否適合進入機會池。如果需求清楚，就審核通過，進入機會池；如果信息不足，就駁回並讓需求方補充。

第二個入口是咨詢公司管理。因為 DaoStore 的承接方不是匿名個人，而是可承責的組織。咨詢公司提交入駐資料後，需要由平台審核。通過後，這家公司才能承接機會池裡的需求。

第三個入口是方案和內容治理。咨詢公司可以提交企業方案，龍蝦騎士可以沉澱教程、問答和個人 Profile。管理員需要確保這些內容是可信的，避免平台變成一堆沒有審核的展示頁。

所以管理員視角的關鍵詞是：審核、准入、治理、風險控制。這一層確保進入交易閉環的需求、公司、方案和人都是可管理的。

錄屏操作點：

- 打開 `/admin/orders`，展示待審核、機會池、已承接等 Tab。
- 指出審核通過後需求進入機會池。
- 打開 `/admin/companies`，展示咨詢公司審核隊列。
- 如有 `/admin/solutions`，展示企業方案審核入口。

## 三、咨詢公司視角

建議畫面：`/opportunities`、`/company-center`

旁白：

第三個身份是咨詢公司。

當管理員把需求審核通過後，需求會出現在機會池。咨詢公司可以在這裡瀏覽可承接需求，根據自身能力和客戶背景判斷是否接單。

這裡要注意，DaoStore 裡的咨詢公司不是只做展示的供應商名片。它是承接責任的組織方。接單後，咨詢公司還需要在「咨詢公司中心」進一步管理交付資源。

在公司中心裡，有三個重要區域。第一是公司 Profile 和企業方案，這代表公司的能力展示。第二是已承接待分配需求，接單後公司需要把需求分派給本公司 active 的龍蝦騎士。第三是成員管理，Owner 和 Admin 可以處理龍蝦騎士主動加入申請，也可以管理正式所屬關係。

這個設計解決的是「誰承責、誰組織、誰交付」的問題。咨詢公司對外承接需求，內部組織龍蝦騎士完成交付，平台則保留整個過程的狀態和審核痕跡。

錄屏操作點：

- 打開 `/opportunities`，展示「可承接需求」和「開放承接」。
- 打開 `/company-center`，展示公司 Profile、企業方案、已承接待分配。
- 指出接單後要選擇龍蝦騎士並點擊分配。
- 展示成員區：Owner、Admin、龍蝦騎士。

## 四、龍蝦騎士視角

建議畫面：`/me`、`/knights/become`、`/users/[id]` 或個人中心中的 Profile 區域

旁白：

最後看龍蝦騎士，也就是 DaoStore 裡的 FDE。

龍蝦騎士不是普通接單用戶，而是具備業務理解、AI Coding、系統集成和 Solution Delivery 能力的個人交付者。第一階段裡，龍蝦騎士身份由平台確認。確認之後，他可以完善自己的 Profile，沉澱教程、問答、聲望和能力展示。

在組織關係上，龍蝦騎士可以主動申請加入一家已審核通過的咨詢公司。這裡有一個邊界：一個龍蝦騎士同一時間最多只能有一家正式所屬公司。這是為了讓交付責任更清楚。

當咨詢公司承接需求後，公司 Owner 或 Admin 會把訂單分派給 active 的龍蝦騎士。龍蝦騎士在個人中心可以看到分派給自己的訂單，然後進入需求跟進、方案推進、交付狀態更新。

所以龍蝦騎士視角的重點不是「搶單」，而是成為可被公司組織、可被平台識別、可沉澱信用的交付者。

錄屏操作點：

- 打開 `/me`，展示公開 Profile、騎士能力、我的需求、分派給我的訂單。
- 打開 `/knights/become`，說明平台確認身份後可申請加入公司。
- 回到 `/me` 或用戶詳情頁，展示教程、問答、聲望、稱號等信用沉澱。

## 五、閉環收束

建議畫面：回到首頁 `/` 或 `/orders`

旁白：

最後把四個角色串起來看。

需求方負責提出真實企業問題，系統幫他把需求整理成可審核、可追蹤的訂單。管理員負責把關需求、公司、方案和內容，確保平台不是失控的撮合市場。咨詢公司是承接和組織交付的責任主體，接單後分派龍蝦騎士。龍蝦騎士則是真正靠近業務現場，把需求推進成可落地 Solution 的交付者。

DaoStore 的核心價值就在這裡：它不是只讓大家看到「有很多 AI 方案」，而是讓一個企業 AI 需求能從提出、被審核、被承接、被分派、被交付，最後形成可復用的 Solution 資產。

這也是我們接下來驗證 DaoStore 的重點：不是看頁面多不多，而是看一個真實需求能不能完整跑通交付閉環。

## 精簡版一分鐘口播

DaoStore 是企業 AI Solution 的交付協作平台。需求方可以用自然語言提交企業需求，系統會先整理成可確認的信息，再進入審核和狀態追蹤。管理員負責審核需求、咨詢公司、方案和平台內容，確保進入流程的需求與供給是可治理的。咨詢公司通過審核後，可以在機會池承接需求，並在公司中心把需求分派給本公司 active 的龍蝦騎士。龍蝦騎士作為 FDE，負責業務理解、AI Coding、系統集成和 Solution Delivery。整套系統要打通的是企業需求從提交、審核、承接、分派、跟進到交付驗收的閉環，讓 AI Solution 不停留在 Demo，而能真正進入企業交付。

## 錄製檢查清單

- 使用 1440px 或 1920px 寬屏錄製，瀏覽器縮放保持 100%。
- 錄製前確認登入身份能看到對應頁面；若無數據，講解空狀態時要說「沒有真實需求時不使用假數據填充」。
- 需求方段落優先展示 `/chat`，不要只展示 `/orders`，因為自然語言入口更符合實際用戶第一步。
- 管理員段落要明確說審核通過後需求才進入機會池。
- 咨詢公司段落要明確說接單後還需要分派龍蝦騎士。
- 龍蝦騎士段落要避免講成自由搶單，重點是身份確認、公司歸屬、被分派後跟進。
- 結尾回到「真實需求完整跑通交付閉環」，不要收束成普通方案商城。
